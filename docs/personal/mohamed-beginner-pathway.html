Anther personal development plan

Mohamed Beginner Pathway

A practical route from cybersecurity student to a confident contributor for Anther's security, QA, integration, notifications, and release-support work.

Your role in plain language

  • Security: protect sensitive information and define who can access what.
  • QA: test features and report problems clearly.
  • Integration: verify that Flutter, Supabase, and notifications work together.
  • Notifications: later support safe appointment reminders and status updates.
  • Release support: help the team decide when a version is ready to share.

You do not need to know everything before contributing. Learn one small concept, apply it to Anther, request a cross-check, then move on.

Week 0

Prepare your environment

Learn

  • Git versus GitHub, branches, commits, pull requests, merge conflicts, .gitignore, and .env.
  • Basic Git commands: status, pull, switch -c, add, commit, diff, and push.

Apply to Anther

  • Read README.md, docs/WORKFLOW.md, and docs/TEAM_CHECKLIST.md.
  • Create feature/mohamed-git-practice.
  • Add docs/personal/learning-log.md with notes on Git, branches, and why .env is private.
  • Make one local commit; do not push until approval.

Week 1

Understand Anther before securing it

  • Learn client-server basics, authentication versus authorization, and the patient/provider/admin/reviewer roles.
  • Create docs/security/data-classification.md.
  • Classify account, appointment, address, provider-credential, medical-record, payment-reference, and log data.
  • Ask Najib about Supabase Auth and Row Level Security; Salah about provider verification; Abdikhalaq about the patient booking journey.

Week 2

Security baseline and threat model

  • Learn confidentiality, integrity, availability, least privilege, broken access control, leaked secrets, and unsafe file links.
  • Create docs/security/threat-model.md and docs/security/security-baseline.md.
  • Cover a patient reading another patient's appointment, an unverified provider receiving bookings, a public document link, and a leaked secret.
  • Ask Najib and Salah to cross-check the controls and workflow states.

Week 3

QA plan and useful bug reports

  • Learn unit, integration, manual, regression, and security testing.
  • Create docs/qa/test-plan.md and docs/qa/acceptance-checklist.md.
  • Write tests for sign-up, sign-in, invalid input, logout, booking, appointment status, and role-based access.
  • Include negative tests such as invalid status changes and attempts to access another patient's information.

Week 4

Flutter and app-level testing

  • Learn basic Dart, Flutter widgets, navigation, forms, validators, and widget tests.
  • Pair with Abdikhalaq to run the Flutter app.
  • Add one basic form-validation widget test in mobile/test/ when a relevant screen exists.
  • Record the results in docs/qa/week-4-results.md.

Week 5

Supabase authorization testing

  • Learn PostgreSQL basics and how Supabase Row Level Security works.
  • With Najib, test fictional patient, provider, admin, and reviewer accounts.
  • Verify patients see only their data, unverified providers are hidden, and verification evidence stays restricted.
  • Record results in docs/qa/week-5-results.md and log failures before push approval.

Week 6

Integration and notification design

  • Learn API requests/responses, Firebase Cloud Messaging, and in-app versus device notifications.
  • Create docs/notifications/notification-plan.md.
  • Define requested, confirmed, changed, cancelled, reminder, and completed events.
  • Use privacy-safe language: “Your appointment status has changed,” not medical details.

Week 7

Release readiness

  • Learn development/test/production environments, regression testing, versioning, and rollback planning.
  • Create docs/qa/release-checklist.md.
  • Test account creation, login, booking, authorization, errors, privacy, and accidental exposure of development information.

Routine for every Anther task

  1. Read the GitHub issue and its acceptance criteria.
  2. Confirm the intended files and create your branch.
  3. Make one focused change and run the relevant checks.
  4. Review the diff for secrets, personal data, and unrelated edits.
  5. Request a peer cross-check using the workflow template.
  6. Resolve feedback, then request project-owner approval before pushing.

Important limits

  • Use fictional data only.
  • Do not test against real patients, providers, payments, or production services.
  • Do not commit keys, passwords, tokens, addresses, or documents.
  • Defer maps, payments, video, chat, and medical-record uploads until formally added to the MVP.
